01 / WORKFLOW

Overview

The project grew from a CLI into a web interface and Docker service, bringing transcription, speaker attribution, minutes, and sharing into one workflow.

02 / SYSTEM

Architecture

The service currently operates on an RTX 4090. The public demo uses sample data; actual speech processing and external API calls run in the internal service.

  1. 01Audio

    faster-whisper

  2. 02Diarize

    pyannote · RTX 4090

  3. 03Minutes

  4. 04Deliver

    Notion · SMTP

03 / PERFORMANCE

Evaluation

The historical “56-minute file, about 28 seconds” record refers to a chunked diarization stage. It is not total transcription-to-delivery latency or a repeated benchmark.

The next operational evidence is per-stage latency, diarization quality, and failure/reprocessing rates, measured without disrupting the active service.

04 / ACCESS

SSO and access control

Google SSO and user/department access boundaries are part of the workflow. The public interface is separated from internal meeting data.

ENGINEERING DECISIONS

Engineering decisions

01

Connect local GPU work with services

Local GPU speech processing and diarization feed structured minutes into storage and delivery steps.

02

Design access around the workflow

Meeting access follows the signed-in user and department context.

03

Measure stages separately

Diarization timing is not presented as full meeting-processing time. Measurements identify input duration, environment, and pipeline stage.

SCOPE & LIMITS

Limitations and scope

  • Internal code and meeting data are private. Demo audio and results are samples.
  • A stage-specific observation is not presented as an end-to-end service SLA.
